## 4. PATRONES ESTABLECIDOS / ACTUALIZADOS

### Patrón NUEVO: Type System Unification Layer (F30)

**Concepto:** Un archivo maestro `domain-enums.ts` define TODOS los enums cross-domain. Cada domain types.ts importa de aquí. Cuando el backend cambia, se actualiza UN archivo.

**Cuándo se aplica:** SIEMPRE que un concepto se usa en 2+ domains.
**Archivos:** `shared/types/domain-enums.ts`
**Patrón de importación:**
```typescript
import { type EventCategory, EVENT_CATEGORY_DISPLAY } from "@/shared/types/domain-enums";
```

### Patrón NUEVO: AI Intelligence Type System (F30)

**Concepto:** Tipos genéricos (`AIPrediction<T>`, `AIAnalysis`, `AIBrief`) que se extienden por domain. Permite reutilización de patrones AI across domains.

**Cuándo se aplica:** Cada vez que un domain crea inteligencia AI (predictions, analysis, narratives).
**Archivos:** `shared/types/ai-intelligence.ts`
**Patrón de extensión:**
```typescript
interface FinancialAnalysis extends AIAnalysis {
  domain: "financial";
  cash_flow_forecast?: { ... };
}
```

### Patrón NUEVO: Conditional HITL Escalation (descubierto en sports_recreation)

**Concepto:** Tool AUTO que escala a HITL basado en parámetros (ej: `purpose == "tournament_block"`).
**Cuándo se aplica:** Cuando una operación regular tiene un caso de uso de mayor riesgo.
**Ejemplo:** `manage_court_reservations` — AUTO para reservas regulares, HITL para bloqueos de torneo.

### Patrón NUEVO: Multi-Source Intelligence (descubierto en sports_recreation)

**Concepto:** Tool de recomendación que combina múltiples fuentes de datos internas (classes + coaching history + equipment) para generar recommendations con confidence scoring.
**Cuándo se aplica:** Tools que cruzan datos de múltiples repositorios del mismo agent.

### Patrón NUEVO: HITL Auto-Approve (descubierto en satisfaction)

**Concepto:** Tool que crea approval request pero lo auto-aprueba inmediatamente. Mantiene trazabilidad sin requerir intervención humana.
**Cuándo se aplica:** Operaciones de socio que deben ser auditables pero no requieren aprobación (ej: encuestas de satisfacción).

## 12. DECISION LOG

| Decisión | Razón | Impacto |
|----------|-------|---------|
| Type System Unification via domain-enums.ts | 5 sistemas de tiers, 2 de age groups, etc. causaban inconsistencias cross-domain | UN archivo maestro reemplaza todas las duplicaciones |
| AI Intelligence Type System via ai-intelligence.ts | Patrones AI repetidos across domains sin reutilización | Generic types + domain aliases permiten reutilización |
| Backend como source of truth para enums | Los 7 values de EngagementLevel del backend son más completos que los 5 del frontend | Legacy mappings permiten migración incremental |
| Propuesta 1+3 como eje arquitectónico, 2+4 como vehículo | 1+3 resuelven el problema de raíz. 2+4 son operación/transición | Claridad en qué es estrategia vs táctica |
| Regla de bloque >30% REWRITE | Múltiples cambios quirúrgicos en mismo archivo desperdician tokens | Optimización de recursos por lectura |
| Conditional HITL escalation (sports_recreation pattern) | Patrón nuevo descubierto: AUTO que escala a HITL por parámetros | Replicable para otros agents |
| HITL Auto-Approve (satisfaction pattern) | Trazabilidad sin intervención humana para operaciones de socio | Replicable para SOCIO portal |
| Domain-specific enums NO van al master | SportType, CulturalCategory, etc. solo se usan en 1 domain | Evita bloat en domain-enums.ts |
| contracts.ts como 2do paso después de master enums | Ya tiene el patrón correcto pero 53 contracts faltantes | Phase B completa la integración |
