1. **BLOQUE A** = líneas EXACTAS que se reemplazan (copiar del archivo actual)

3. **Si es INSERTAR** (no reemplazar): decir "después de la línea X, antes de la línea Y" con las líneas literales de referencia
4. **NUNCA** decir "agregar X al existente" — siempre reemplazar el bloque completo
5. **NUNCA** instrucciones conceptuales — siempre código exacto
6. **Si es REWRITE (>30%)**: entregar el archivo completo, no bloque por bloque
7. **Trabajar por APPENDS** en archivos grandes (factories.ts, contracts.ts, mock-registry.ts)

## 4. PATRONES ESTABLECIDOS / ACTUALIZADOS

### Patrón NUEVO: Backend Tool Migration (F26a)

**Concepto:** Workflow para migrar una tool de mock-only a backend real.

**Pasos:**
1. Auditar agent actual (pattern de tools, return shape, decorators)
2. Auditar models existentes (Pydantic pattern, enums, ConfigDict)
3. Auditar repo (métodos CRUD + compute existentes)
4. Auditar mock factory (shape como source of truth para nuevos models)
5. Auditar executive dashboard (verificar si ya existe con otro nombre)
6. Crear Pydantic models nuevos si necesario
7. Crear repo methods nuevos si necesario
8. Crear MCPTool en agent como thin wrapper
9. Alinear mock factory + contracts con nuevos models
10. Verificar registry entry

**Cuándo se aplica:** Cualquier tool mock-only que necesita backend real.
**Fases donde se replica:** F26b (wellness_correlate + wellness_insights), F26c+ (otros agents).

### Patrón ACTUALIZADO: Mock Conventions (F26a)

**Convenciones descubiertas:**
- Factory prefix: `createMock` (no `create`)
- Factory params: `params?: { key?: type }` — optional, con defaults
- Contract naming: `{tool_name}_Contract`
- Registry entry: `(params) => createMockXxx(params)`
- Append strategy para archivos grandes (>8000 líneas)

### Patrón ACTUALIZADO: Dual Paradigma Architecture

```
Paradigma 1 (Executive): Hardcoded demo data → siempre muestra algo
Paradigma 2 (Domain): Computed from repo → producción real
```

No confundir tools de Paradigma 1 con Paradigma 2. `get_financial_overview` ≠ `get_financial_summary`.

### Patrones que aplicaron sin cambios:
- P1 (Auto-load + On-demand)
- P9 (Defensive Data Rendering)
- P25 (Formato entrega)
- Compute en repo para wellness (consistente con get_recommendations)
- Compute en agent para finance (consistente con generate_ai_analysis)

| 1 | Compute en repo para wellness predict/anomalies | Compute en agent (patrón finance) | Consistente con `get_recommendations()` y `generate_report()` existentes en wellness_repo | Wellness usa repo, Finance usa agent — ambos válidos |

| 5 | `WellnessRiskLevel` reutilizado para prediction Y anomaly severity | Enums separados por context | Un solo vocabulario de severidad en wellness | Menos tipos, más consistencia |
| 6 | `FinancialRevenueLine` como model nuevo | Reutilizar `RevenueSource` existente | Shapes incompatibles: RevenueSource tiene name/label/share_pct, summary necesita source/amount/percentage | Model dedicado para cada shape |
| 7 | `FinancialExpenseLine` como model nuevo | Reutilizar `BudgetLine` existente | Shapes incompatibles: BudgetLine tiene budgeted/spent/remaining, summary necesita category/amount/percentage/variance | Model dedicado |
| 8 | F26a scope = 4 tools (no todas las mock-only) | Migrar todas las ~20 mock-only tools | Paradigma 1 es intencional. Solo migrar Paradigma 2 | Scope claro y acotado |

| 11 | `WellnessAnomaly.expected_min/max` typed | `expected_range: string` | Typed > untyped. Calculable, más útil para frontend | Model más expresivo |
| 12 | AR aging calcula desde `due_date` | Calcular desde `created_at` | `due_date` indica cuándo se esperaba el pago — más relevante para aging | Datos más accionables |
| 13 | Factory prefijo `createMock` | `create` | Convención existente del proyecto descubierta durante B5 | Consistencia con ~8000 líneas existentes |
| 14 | No proponer bloques sin leer código primero | Proponer desde descripciones | Usuario corrigió: "no conocés ningún repo así que sería importante conocer el repo específico" | Proceso mental paso 1: leer código real |
