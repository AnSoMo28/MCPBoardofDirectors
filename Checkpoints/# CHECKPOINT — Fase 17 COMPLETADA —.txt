## 3. PATRONES ESTABLECIDOS

### Patrón: Client-Side AI Advisor (creado en Fase 17)

**Concepto:** Un hook de React que computa insights estratégicos de datos ya en caché de React Query. Cero llamadas al backend. Cero latencia. Aparece como banner en el top del dashboard.

**Niveles:**

```
Nivel 0: Dashboard queries (auto-load, staleTime)
   ↓ datos en caché
Nivel 1: useRecommendationAdvisor(datos en caché) → AdvisorInsight[]
   ↓ 7 reglas computacionales
Nivel 2: <AdvisorBanner /> → render condicional (solo si hay insights)
   ↓ click "Ir"
Nivel 3: setActiveTab(targetTab) → navega al tab relevante
```

**Tipo de dato:**

```typescript
type AdvisorInsight = {
  id: string;
  title: string;
  reasoning: string;
  impact: "high" | "medium" | "low";
  targetTab: string;
  confidence: number; // 0-100
};
```

**Reglas computacionales implementadas:**

| # | Regla | Input | Output | Impact |
|---|-------|-------|--------|--------|
| 1 | Pricing pendientes | pendingPricings.length > 0 | "N optimizaciones, X alto riesgo, impacto +₡N" | HIGH/MEDIUM |
| 2 | Alta demanda | interest≥70, requests≥20 | "N sugerencias de alta demanda: X, Y, Z" | HIGH |
| 3 | Sin insights | insights.length === 0 | "Sin informes trimestrales" | MEDIUM |
| 4 | Insights stale | latestInsight > 90 días | "Último informe hace N días" | MEDIUM |
| 5 | Baja satisfacción | satisfaction < 4.0 | "Satisfacción X/5.0, áreas: A, B" | HIGH |
| 6 | Backlog sugerencias | pendingSuggestions ≥ 5 | "N sugerencias acumuladas" | MEDIUM |
| 7 | Recomendaciones sin implementar | latestInsight.recommendations > 0 | "N recomendaciones sin implementar" | MEDIUM |

**Cuándo se aplica:**
- Cualquier dashboard que tiene múltiples queries de diferentes dominios
- Donde los datos ya cargados pueden cruzarse para producir insights
- Donde el usuario se beneficia de "qué hacer ahora" sin tener que analizar datos

**Fases futuras donde se replica:**
- F18: FinancialDashboard — Advisor financiero (costos, revenue, proyecciones)
- F19: EventOrchestrator — Advisor de eventos (conflictos, asistencia, optimización)
- F20: Cross-Agent Health — Advisor global (salud del sistema, anomalías cross-agente)

### Patrón: CRUD con Action Routing (pre-existente, documentado aquí)

**Cuándo se usa:** Tools que soportan múltiples operaciones (list, get, create, update_status) bajo un solo nombre de tool, diferenciadas por param `action`.

**Ejemplo:**
```typescript
useMCPQuery("proactive_recommendation", "optimize_pricing", { action: "list" })
useMCPMutation("proactive_recommendation", "optimize_pricing", { action: "create", ... })
```

**Diferencia con ExecutiveDashboard:** Donde cada operación es una tool separada (`get_executive_summary`, `detect_anomalies`).

## 4. DECISIONES DE DISEÑO

| Decisión | Alternativa descartada | Razón |
|----------|----------------------|-------|
| Advisor como hook + banner inline en shell | Tab separada de "AI Advisor" | Un tab más sería 8vo tab. Advisor tiene sentido como contexto global que aparece siempre, no como vista escondida |
| Advisor consume cache (3 queries duplicadas en shell) | Advisor hace sus propias queries | React Query deduplica — las mismas 3 queries ya las hace el Overview. Shell pre-calienta caché, Overview carga al instante |
| Advisor como expansible (colapsable) | Siempre visible, no colapsable | Si hay 0 insights, no ocupa espacio. Si hay insights, usuario puede colapsar después de verlos |
| 7 reglas computacionales fijas | Motor configurable con reglas dinámicas | Para 8 tools, reglas fijas son más simples, auditableas y mantenibles. Motor configurable es over-engineering |
| "Ir" en cada insight navega al tab | "Ir" abre modal / pre-llena formulario | Navegación al tab es suficiente como primer paso. Pre-llenar forms es F21 (mutations inteligentes) |
| Auditoría de sub-componentes sin re-escritura | Re-escritura completa como E2 | Los sub-componentes están bien construidos. Solo necesitan fixes cosméticos (fonts, formatters). Re-escritura sería waste |
| Keyframes consolidados en shell pero NO eliminados de sub-componentes | Eliminar de sub-componentes | Los sub-componentes pueden montarse independientemente (otros dashboards, tests). Mantener keyframes propios es defensivo. Limpieza en F22 |
| 3 sub-componentes no auditados (SocialClusters, SchedulingConflicts, PredictAttendance) quedan pendientes | Auditar ahora | No bloquean el Advisor. Son componentes de tab individuales. Se auditan cuando se trabaje su F22 polish |

## 8. VISIÓN DE IA — Cómo estamos construyendo una herramienta de decisión inteligente

### El problema que resolvemos

La mayoría del software de gestión de clubes es **un repositorio de datos** — te muestra lo que pasó. Nuestro sistema es un **sistema de decisión** — te dice qué hacer y por qué.

### Los 4 niveles de inteligencia que estamos implementando

```
Nivel 1: DATOS (lo que ya existía)
├── Queries al backend
├── Visualización de KPIs
├── Charts y tablas
└── "¿Qué está pasando?"

Nivel 2: CONTEXTO (lo que construimos en E1-E4)
├── Auto-load + staleTime optimization
├── On-demand sections (CTA → loading → results)
├── Types source of truth (backend 1:1)
└── "¿Qué necesito ver ahora?"

Nivel 3: INTELIGENCIA CLIENT-SIDE (lo que innovamos)
├── AI Advisors (useRecommendationAdvisor, etc.)
├── Reglas computacionales de 7+ factores
├── Cross-domain analysis (pricing × suggestions × insights)
├── Impact scoring (high/medium/low)
├── Confidence scoring (0-100)
├── 0 API calls, 0 tokens, 0ms
└── "¿Qué debería hacer y por qué?"

Nivel 4: ACCIÓN INTELIGENTE (F21 — el futuro)
├── Pre-filled mutation params desde Advisor insights
├── One-click execute: Advisor → Form → HITL → Approval
├── Batch actions: "Aprobar todas las optimizaciones de bajo riesgo"
├── AI-generated communication drafts
└── "Ejecutá esto, ya lo analicé"
```

### Lo que hace único a nuestro sistema

| Característica | Software tradicional | Nuestro sistema |
|---------------|---------------------|-----------------|
| Datos | Tablas y charts | Tablas, charts + Advisor que interpreta |
| Análisis | El usuario analiza | El sistema analiza y propone |
| Decisiones | El usuario decide qué mirar | El sistema prioriza qué mirar |
| Acciones | El usuario navega forms | El sistema pre-llena y guía |
| Cross-domain | Cada módulo es aislado | Advisor cruza pricing × activities × insights |
| Inteligencia | Backend ML (latencia, tokens) | Client-side compute (0ms, 0 tokens) |
| Personalización | Genérico para todos | Basado en datos reales del club específico |
