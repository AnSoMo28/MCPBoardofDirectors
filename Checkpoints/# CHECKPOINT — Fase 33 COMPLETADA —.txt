## 1. LO QUE ESTAMOS CONSTRUYENDO


### Castillo AI Platform = "Sistema de Decisión Inteligente"

NO es un dashboard. NO es un ERP. NO es un CRM. Es un sistema donde:

- Los **datos** se transforman en **contexto** (sabemos qué está pasando)
- El **contexto** se transforma en **inteligencia** (sabemos qué significa)
- La **inteligencia** se transforma en **acciones** (sabemos qué hacer)
- Las **acciones** se transforman en **resultados** (medimos el impacto)

**Castillo AI Platform** = Sistema de Decisión Inteligente para un country club privado en Costa Rica.

- **13 dominios** de inteligencia (sports, facilities, events, finance, communications, etc.)
- **Patrón por dominio:** Backend agent → MCP tools → Mock system → Frontend hooks → Advisor rules → Dashboard UI
- **Intel client-side:** 0ms latencia, 0 tokens API, 100% computed en browser
- **Cross-domain:** Señales entre dominios (ej: sports → facilities: "canchas deportivas al 85%")
- **ApprovalQueue:** Tools HITL pasan por aprobación antes de ejecutar

**Esta sesión:** Construimos el dominio **Facilities (F33)** completo — backend + frontend — desde cero.

## 4. PATRONES ESTABLECIDOS / ACTUALIZADOS

### Patrón NUEVO: LiveOccupancyBoard (F33)

**Concepto:** Real-time facility grid con pulse indicators, capacity bars, y hover-reveal reservations — el "differentiator" visual del dominio Facilities.

**Niveles:**
```
Nivel 1: PulseIndicator — 5 statuses (available/busy/occupied/maintenance/closed), animación ping configurable
Nivel 2: CapacityBar — animated progress con color por nivel (4 tier: emerald/teal/amber/rose)
Nivel 3: FacilityCard — type emoji, type display, status hours, current activity, maintenance overlay, upcoming reservations (hover), quick-book button (hover)
Nivel 4: LiveOccupancyBoard — merge occupancy + reservations para calcular live status en tiempo real (occupied si reserva activa, busy si reserva en <30min)
```

**Cuándo se aplica:** Cualquier dominio que tiene espacios físicos con estado en tiempo real.
**Fases futuras donde se replica:** Events (venue availability), Wellness (spa rooms)

## 6. DECISIONES DE DISEÑO

| # | Decisión | Alternativa descartada | Razón | Impacto |
|---|---------|----------------------|-------|---------|
| 1 | Advisor 100% client-side (0ms, 0 tokens) | LLM-based advisor | Patrón ya establecido en Sports domain — consistencia y performance | Todos los dominios siguen este patrón |
| 2 | Intelligence queries: `enabled: false` por defecto, `enabled: true` solo cuando tab activo | Auto-load all on dashboard mount | Rule #19 — evitar llamadas innecesarias, ahorrar bandwidth | Patrón on-demand se replica en todos los dashboards |
| 3 | `computeMaintenanceUrgency` en frontend types.ts | Query backend para urgency score | Consistencia con Sports domain (compute client-side), evita round-trip | Scoring siempre disponible sin API call |
| 4 | MaintenanceStatus transitions hardcoded en MaintenanceScoring | Query backend para transitions disponibles | Patrón P28 ya establecido, transitions son conocidas y estáticas | Se puede migrar a backend en futuro |
| 5 | EventSetupPanel con mock data inline | Crear tool de listado de event setups | `coordinate_event_setup` es mutation-only en backend, no tiene list tool | Se migrará cuando se cree tool de listado |
| 6 | InspectionPanel recibe `inspections={undefined}` en dashboard | Auto-load inspections en batch principal | Consistencia con Sports (TournamentPanel carga sus propios datos) | Se puede habilitar auto-load en futuro |
| 7 | BookingFormModal via `createPortal(document.body)` | Render inline en componente | Patrón establecido para modales, evitar z-index issues con parent containers | Todos los modales siguen este patrón |
| 8 | Utilization level: 4 tiers (low/medium/high/critical) con thresholds 40/70/90 | Continuous gradient | Mejor UX para quick visual scanning, colores distinguishables | Se usa en Heatmap, ROI, KPIs |
