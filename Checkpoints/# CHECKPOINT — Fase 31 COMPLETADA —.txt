## 4. PATRONES ESTABLECIDOS / ACTUALIZADOS

### Patrón NUEVO: Cultural Engagement Motor (F31)

**Concepto:** Motor proactivo que genera propuestas de actividades culturales basándose en datos cross-domain (patrones de membresía, finanzas, estacionalidad).

**Niveles:**
```
[Nivel 1]: generate_cultural_proposals tool en backend — ejecuta análisis cross-domain
[Nivel 2]: Advisor action que sugiere "Generar propuestas" cuando engagement score < 40
[Nivel 3]: CulturalAdvisorBanner muestra propuestas como insights accionables
```

**Ejemplo de código:**
```typescript
// En useCulturalAdvisor.ts — Rule: LOW_ENGAGEMENT
{
  id: 'low_engagement',
  condition: (ctx) => ctx.analytics?.avg_attendance_30d < 15,
  layer: 'proactive',
  severity: 'high',
  insight: 'Participación cultural por debajo del promedio',
  action: {
    label: 'Generar propuestas de actividades',
    tool: 'generate_cultural_proposals',
    params: { member_preferences: ctx.memberPrefs },
    approval: 'AUTO',
  },
}
```

**Cuándo se aplica:** Cuando un dominio necesita pasar de reactivo a proactivo — no solo mostrar datos, sino sugerir acciones.
**Fases futuras donde se replica:** F32 (Sports — Engagement Motor), F33+ (otros dominios)
**Archivos donde ya está implementado:** `useCulturalAdvisor.ts`, `CulturalAdvisorBanner.tsx`

## 6. DECISIONES DE DISEÑO

| # | Decisión | Alternativa descartada | Razón | Impacto |
|---|---------|----------------------|-------|---------|
| 1 | ProgramStatus separado de EventStatus | Reusar EventStatus genérico | Los programas tienen estado `enrolling` que no aplica a eventos | Todos los programas usan ProgramStatus, eventos siguen con EventStatus |
| 2 | Calendar agrupa 3 entity types (events, exhibitions, programs) | Calendario solo para eventos | El usuario necesita ver TODA la actividad cultural en un solo timeline | Calendar tool retorna CalendarItem[] polimórfico |
| 3 | Engagement Motor como tool separado | Lógica dentro del Advisor | El motor necesita acceso a datos cross-domain que el Advisor client-side no tiene | generate_cultural_proposals es server-side, Advisor solo lo sugiere |
| 4 | 5 form modales (3 HITL + 2 AUTO) | Un solo modal genérico | Cada tipo de actividad tiene campos únicos que merecen UX específica | 5 modales independientes, reutilizables |
| 5 | CulturalIntelligencePanel como componente separado del Dashboard | Inline en el Dashboard | El panel de 9 dimensiones es complejo (~350 líneas) y se carga on-demand (Rule #19) | Panel se monta solo cuando el usuario hace click en "Análisis Profundo" |
| 6 | Venue recommendations basadas en datos históricos | Recomendaciones estáticas | Las recomendaciones deben adaptarse al uso real del club | VenueIntelligence calcula confidence basado en booking history |
| 7 | Enrollment bar con 3 umbrales de color (75/40) | Dos umbrales (50/25) | El 75% marca "lleno", el 40% marca "preocupante" — mejor distribución visual | Programas muestran urgencia visual clara |
| 8 | Status transitions como hover-reveal | Siempre visibles | Reduce clutter visual, el hover indica "estoy interactuando con este card" | UX más limpia, descubrimiento por exploración |

**CONTEXTO ESTRATÉGICO — El mismo problema que Cultural:**

El backend de Sports & Recreation probablemente tiene el mismo patrón que Cultural antes de F31:
- Un agent con CRUD básico pero sin tools de inteligencia
- Models sin enums específicos para la complejidad deportiva
- Sin analytics aggregation en el repo
- Sin domain expert prompt
- Sin engagement motor

**El proceso creativo para F32 debe contemplar:**

1. **Base Cultural como referencia** — Los mismos patrones (Advisor de 15 rules, Intelligence Panel de 9 dimensiones, Engagement Motor, Calendar unificado, form modals HITL/AUTO) se replican pero adaptados al dominio deportivo.

2. **Libertad creativa total** — El frontend deportivo debe ser tan innovador como el cultural pero con su propia identidad visual. Donde Cultural usa gold/sage/teal, Sports puede usar energía, movimiento, dinamismo.

3. **Expertise Senior Master en UI/UX** — El dashboard deportivo debe sentirse diferente al cultural:
   - Layouts que evocan movimiento (asimetría dinámica vs la elegancia simétrica del cultural)
   - Visualizaciones deportivas (court maps, team rankings, skill progressions)
   - Gamification elements (badges, streaks, leaderboards)
   - Time-slot visualization para canchas
   - Weather integration para deportes outdoor

4. **Cross-domain factors** — Sports impacta:
   - **Memberships:** Deportes populares retienen socios
   - **Finance:** Court rentals, equipment, instructor fees
   - **Events:** Torneos son mega-eventos
   - **Cultural:** Eventos deportivos-culturales híbridos

5. **Diferenciador propuesto:** **Sports Performance Engine** — Motor que analiza patrones de uso deportivo del socio y sugiere:
   - Clases para mejorar habilidades específicas
   - Partners de juego compatibles (matching)
   - Torneos apropiados para su nivel
   - Horarios óptimos basados en su historial

### Sección 6: Advisor Architecture — ACTUALIZAR capas

```markdown
**5 Layers (actualizado):**
1. **Context** — Construye el contexto del dominio desde los datos
2. **Reactive** — Responde a problemas actuales (attendance baja, budget alto)
3. **Preventive** — Alerta sobre problemas emergentes (no galas programadas, seasonal gap)

5. **Proactive** — Genera nuevas oportunidades (Engagement Motor, cross-domain suggestions)

### Sección 7: Reglas — AGREGAR regla del Engagement Motor

```markdown
**Regla: Engagement Motor Pattern**
Cada dominio de alto valor (Cultural, Sports, Wellness, F&B) debe tener un "Engagement Motor" — 
una tool MCP server-side que genere propuestas proactivas basándose en datos cross-domain.
El Advisor solo SUGIERE ejecutar el motor; el motor hace el análisis pesado.
```
