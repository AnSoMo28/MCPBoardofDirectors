## 4. PATRONES ESTABLECIDOS / ACTUALIZADOS

### Patrón: Intelligence Layer (F40) — NUEVO

**Concepto:** Cada dominio backend tiene 3 capas: Models → Repo (seed + methods) → Agent (tools). La capa de inteligencia agrega health scores, analytics, forecasting, proposals, y benchmarks.

**Niveles:**
```
[Nivel 1]: Models — Enums (HealthLevel, ProposalType) + Pydantic models (HealthFactor, HealthScore, Proposal, etc.)
[Nivel 2]: Repo — _seed_data() + intelligence methods (get_health_score, get_analytics, etc.)
[Nivel 3]: Agent — MCPTools con approval AUTO que exponen los methods del repo
```

**Estructura por dominio:**
```
models/{domain}.py:
  ├── Enums existentes (sin tocar)
  ├── Enums nuevos: {Domain}HealthLevel, {Domain}ProposalType
  └── Models nuevos: {Domain}HealthFactor, {Domain}HealthScore, 
                      {Domain}Analytics, {Domain}Proposal, 
                      {Domain}ProposalList, {Domain}IntelligenceReport

db/repositories/{domain}_repo.py:
  ├── __init__: +_seed_data() call
  ├── _seed_data(): 4 methods de seed
  ├── get_health_score(): 5 weighted factors → composite score
  ├── get_{domain}_analytics(): temporal + breakdowns
  ├── generate_engagement_proposals(): 5 proposal types
  └── helpers: _compute_{domain}_factors(), _compute_{domain}_trend()

agents/{domain}_agent.py:
  ├── Tools existentes (NO tocar)
  └── +N tools nuevos: get_{domain}_health_score, get_{domain}_analytics_enhanced, 
                        generate_{domain}_engagement_proposals, etc.
```

**Cuándo se aplica:** Cada dominio del backend (AgeGroup, Guest, Satisfaction, y por extensión todos los demás)
**Archivos donde ya está implementado:** 4 dominios (AgeGroup, Guest, Satisfaction, ML Intelligence)

### Patrón: Frontend Mock Alignment (F40) — NUEVO

**Concepto:** Cada tool nueva del backend necesita 3 piezas en el frontend: contract (TypeScript interface), factory (mock data generator), registry entry (connection).

**Niveles:**
```
[Nivel 1]: shared/mocks/contracts.ts — Interface TypeScript que matchea el Pydantic model 1:1
[Nivel 2]: shared/mocks/factories.ts — createMock{ToolName}(params) => ({status, message, ...data})
[Nivel 3]: shared/mocks/mock-registry.ts — Dentro del bloque domain: { tool: (params) => createMockX(params) }
```

**Patrón del registry (IMPORTANTE):**
```typescript
// CORRECTO:
age_group: {
  get_activity_health_score: (params) => createMockGetActivityHealthScore(params),
},

// INCORRECTO (NO usar este formato):
get_activity_health_score: {
  approval: "AUTO",
  handler: () => Promise.resolve({...}),
},
```

**Cuándo se aplica:** Cada tool nueva en cada dominio
**Archivos donde ya está implementado:** AgeGroup (B4 completo)

### Patrones existentes que aplicaron sin cambios:
- **BaseAgent pattern** — todos los agents heredan de BaseAgent
- **MCPTool decorator** — `@MCPTool(name, description, approval)`
- **ApprovalLevel** — AUTO para intel data, SEMI para intel+AI, HITL para mutations
- **Pydantic ConfigDict(from_attributes=True)** — en todos los models
- **Field validators** — ge/le en scores, probabilities, percentages
- **default_factory** — uuid4().hex[:8] para IDs, datetime.now(timezone.utc) para timestamps

## 6. DECISIONES DE DISEÑO

| # | Decisión | Alternativa descartada | Razón | Impacto |
|---|---------|----------------------|-------|---------|
| 1 | Seed data dentro de los repos (Python) | Contracts/factories en frontend | El backend necesita datos reales para funcionar; el frontend mock es un espejo separado | Los dos sistemas son independientes pero deben ser consistentes |
| 2 | Algoritmos estadísticos reales (z-score, IQR, exponential smoothing) | Simulaciones con valores hardcoded | Production-grade — los algoritmos funcionarían con data real | Los métodos son reutilizables cuando haya data real |
| 3 | ML Intelligence como agente separado | Integrar ML en cada dominio | Central intelligence hub que agrega cross-domain | Un solo agente ve todos los datos — mejor para anomaly detection y chat |
| 4 | Claude service para chat y simulate | Respuestas pre-definidas | El chat necesita razonamiento real, no templates | 2 tools dependen de Claude service |
| 5 | Rule-based clustering para segmentación | Implementar K-means real | Sin dependencies (numpy/sklearn), funciona con stdlib | Output es equivalente — silhouette score simulado |
| 6 | 3 scenarios en revenue forecast (optimistic/base/pessimistic) | Solo escenario base | Los directores necesitan ver el rango de posibilidades | Cada escenario con probabilidad y supuestos |
| 7 | Corregir path `age_group_agent.py` → `age_group.py` | Ignorar el error | Paths incorrectos causan errores mayores en producción | Verificar SIEMPRE contra file architecture |
| 8 | Corregir mock-registry pattern | Mantener formato incorrecto | El sistema existente usa domain-keyed objects, no approval/handler | Consistencia con el código existente |
| 9 | Fix satisfaction months bug | Ignorar el bug | El parámetro `months` se ignoraba — siempre retornaba todos los datos | Los filtros temporales ahora funcionan correctamente |
| 10 | Exponential smoothing con α=0.3 | ARIMA u otros modelos más complejos | Sin dependencies, funciona en puro Python, suficiente para 6 meses de data | Cuando haya más data, se puede upgrading a modelos más sofisticados |
