```

  ├── Enums: {Domain}HealthLevel, {Domain}ProposalType
  └── Models: {Domain}HealthFactor, HealthScore, Analytics, Proposal, etc.

  └── +N @MCPTool: get_health_score, analytics_enhanced, proposals, etc.

```

```
  └── +N createMock{ToolName}(params) → {status, message, ...data}

  └── domain: { tool: (params) => createMockX(params) }
```

## 6. DECISIONES DE DISEÑO

| # | Decisión | Razón | Impacto |
|---|---------|-------|---------|
| 1 | Seed data en repos Python (no contracts factories) | Backend necesita datos reales; frontend mock es espejo | Dos sistemas independientes pero consistentes |
| 2 | Statistical algorithms reales (z-score, IQR, exp smoothing) | Production-grade, sin dependencies | Reutilizable con data real |
| 3 | ML Intelligence como agente separado transversal | Central hub que ve TODOS los dominios | Mejor para cross-domain anomaly detection |
| 4 | Claude para chat + simulate | Necesita razonamiento real | 2 tools dependen de Claude service |
| 5 | Rule-based clustering (no K-means) | Sin dependencies numpy/sklearn | Output equivalente |

| 10 | 5 enums reusados, no duplicados | MemberHealthLevel ya cubre 4 health levels idénticos | Sin duplicación |
| 11 | Section-scoped imports en contracts.ts | Patrón existente del archivo (cada sección independiente) | Consistencia |
