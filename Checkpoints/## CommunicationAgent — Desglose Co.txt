### Tool 1: `broadcast_club_announcement` — 🔴 HITL

**Propósito:** Enviar anuncio masivo a socios del club. Siempre requiere aprobación admin.

**Parámetros de entrada:**

| Param | Tipo | Requerido | Default | Validación | Notas |
|-------|------|-----------|---------|-----------|-------|
| title | str | Sí | "" | No vacío | Título del anuncio |
| body | str | Sí | "" | No vacío | Contenido |
| announcement_type | str | No | "general" | Validado contra `AnnouncementType` | |
| channels | str | No | "email" | CSV → `NotificationChannel` enum | Multi-canal via CSV |
| target_audience | str | No | "all" | Sin validación | **Sin enum — acepta cualquier string** |
| scheduled_at | str | No | "" | Sin formato | **Si vacío → envío inmediato post-aprobación** |
| priority | int | No | 1 | Sin validación de rango | 1-5? ¿1 es más alto o más bajo? |
| requires_acknowledgment | bool | No | False | — | ¿Socio debe confirmar lectura? |
| notes | str | No | "" | — | |

**Flujo HITL:**
1. Valida title, body, announcement_type
2. Parsea channels CSV a lista de `NotificationChannel`
3. Crea approval request con `approver_roles=["admin"]`
4. `affected_count=0` — **no sabe cuántos socios recibirán el anuncio**
5. Post-aprobación → `execute_announcement()` crea y marca como SENT inmediatamente

**Flujo post-aprobación (`execute_announcement`):**
1. Crea `CreateAnnouncement` con todos los datos
2. `repo.create_announcement(data)` — persiste
3. `repo.update_announcement(id, {status: SENT, sent_at: now})` — marca enviado
4. `repo.create_log(notification_type="announcement", ...)` — crea log
5. **`recipient_count=0` en el log** — no registra a cuántos se envió

**Shape de respuesta (pending):**

```json
{
  "status": "pending_approval",
  "request_id": "uuid",
  "message": "📢 Anuncio '{title}' creado. Esperando aprobación del administrador.",
  "details": {
    "title": "string",
    "announcement_type": "general",
    "channels": ["email"],
    "target_audience": "all",
    "priority": 1
  }
}
```

**Shape de respuesta (post-aprobación):**

```json
{
  "status": "success",
  "message": "📢 Anuncio '{title}' enviado exitosamente.",
  "announcement": {
    "id": "uuid",
    "title": "string",
    "body": "string",
    "announcement_type": "general",
    "channels": ["email"],
    "target_audience": "all",
    "status": "sent",
    "sent_at": "ISO datetime",
    "priority": 1,
    "requires_acknowledgment": false,
    "created_by": "string",
    "created_at": "ISO datetime"
  }
}
```

**Hallazgos:**

| # | Hallazgo | Severidad | Impacto |
|---|---------|-----------|---------|
| 1 | **`target_audience` no tiene enum ni validación** — acepta "all", "vip", "tier:platino", cualquier cosa | ALTA | Frontend no sabe qué opciones mostrar. Si el repo no filtra, ¿qué pasa? |
| 2 | **`recipient_count=0` en approval request Y en log** — no hay tracking de alcance real | ALTA | Sin métrica de "a cuántos socios llegó". Imposible calcular open rate |
| 3 | **`scheduled_at` se ignora en execute** — el anuncio se envía inmediatamente post-aprobación, aunque `scheduled_at` sea en el futuro | ALTA | Si staff programa para mañana y admin aprueba hoy, se envía hoy |
| 4 | `priority` sin rango definido — ¿1 es urgente o 5 es urgente? | MEDIA | Ambigüedad semántica. Convención no documentada |
| 5 | `requires_acknowledgment` no se implementa — el campo existe pero no hay tracking de acknowledgments | ALTA | Feature fantasma: el socio nunca ve "confirmar lectura" |
| 6 | Sin campo `expires_at` — ¿cuándo deja de ser relevante un anuncio? | MEDIA | Anuncios de eventos pasados siguen visibles |
| 7 | Sin preview/test send — admin aprueba sin ver cómo se verá el anuncio en email/push | MEDIA | Errores de formato llegan directo al socio |
| 8 | Sin deduplication — mismo anuncio puede aprobarse múltiples veces | BAJA | Doble envío si admin hace click dos veces |
| 9 | Sin personalización del body — `body` es texto plano, sin template variables `{{name}}`, `{{tier}}` | ALTA | Anuncio masivo sin personalización = spam genérico |

**AnnouncementTypes disponibles (implícito):**

| Tipo | Uso típico | Prioridad sugerida |
|------|-----------|-------------------|
| `general` | Avisos generales | 3 |
| `event` | Anuncios de eventos | 2 |
| `promotion` | Promociones, descuentos | 4 |
| `policy_change` | Cambios de reglamento | 1 (alta) |

**Frontend destino:** `AnnouncementBoard.tsx` (listado), `CommunicationCenter.tsx` (crear), `ApprovalQueue.tsx` (pendiente)

### Tool 2: `manage_emergency_broadcast` — 🔴 ALWAYS_HUMAN (doble confirmación)

**Propósito:** Alerta de emergencia masiva a TODOS los socios por TODOS los canales. Nivel máximo de aprobación.

**Parámetros de entrada:**

| Param | Tipo | Requerido | Default | Validación |
|-------|------|-----------|---------|-----------|
| title | str | Sí | "" | No vacío |
| body | str | Sí | "" | No vacío |
| emergency_type | str | No | "security" | Validado contra `EmergencyType` |
| channels | str | No | "push,sms,whatsapp" | CSV → enum. **Default ya incluye 3 canales** |
| notes | str | No | "" | — |
| requested_by | str | No | "system" | — |

**Flujo ALWAYS_HUMAN:**
1. Valida title, body, emergency_type
2. Parsea channels (default: push + sms + whatsapp — los canales más inmediatos)
3. Crea approval request con `ApprovalLevel.ALWAYS_HUMAN`
4. `affected_count=0` — **again, no sabe cuántos socios**
5. Post-aprobación → `execute_emergency_broadcast()` envía inmediatamente

**Diferencias clave vs announcement:**

| Aspecto | Announcement | Emergency |
|---------|-------------|-----------|
| Aprobación | HITL (1 paso) | ALWAYS_HUMAN (doble confirmación) |
| Default channels | email | push, sms, whatsapp |
| Velocidad | Puede programarse | Inmediata siempre |
| Target | configurable | Todos (implícito) |
| Prioridad | configurable | Máxima (implícita) |

**Flujo post-aprobación (`execute_emergency_broadcast`):**
1. Crea `CreateEmergencyBroadcast`
2. Marca como SENT
3. Log con `notes=f"EMERGENCY: {emergency_type}"`
4. `recipient_count=0` — **mismo problema que announcement**

**Shape de respuesta (pending):**

```json
{
  "status": "pending_approval",
  "request_id": "uuid",
  "message": "🚨 Alerta de emergencia '{title}' creada. Requiere doble confirmación del administrador.",
  "details": {
    "title": "string",
    "emergency_type": "security",
    "channels": ["push", "sms", "whatsapp"]
  }
}
```

**Hallazgos:**

| # | Hallazgo | Severidad | Impacto |
|---|---------|-----------|---------|
| 1 | **Sin geolocalización** — emergencia de "evacuación" va a TODOS, incluso socios que no están en el club | ALTA | Falso positivo masivo. Socio en su casa recibe alerta de evacuación del club |
| 2 | **Sin escalación automática** — si el admin no está disponible, la emergencia espera | ALTA | Emergencias reales no pueden esperar aprobación humana. Debería haber auto-approve después de X minutos con override |
| 3 | **`recipient_count=0`** — no se registra a cuántos llegó la alerta | ALTA | En emergencia real, necesitas saber quién recibió y quién no |
| 4 | Sin confirmación de recepción (read receipt / acknowledgment) | ALTA | En evacuación, necesitas saber quién confirmó que leyó la alerta |
| 5 | Sin retry mechanism — si push falla, no reintenta por SMS | ALTA | En emergencia, delivery guarantee es crítico |
| 6 | Sin template pre-aprobado — se escribe body desde cero cada vez | MEDIA | En emergencia real, no hay tiempo redactar. Debería haber templates pre-aprobados por tipo |
| 7 | Sin TTL/time-to-live — la alerta queda activa indefinidamente | MEDIA | "Todo claro / All clear" para cancelar la emergencia |
| 8 | Sin link a mapa o instrucciones de evacuación | MEDIA | Body es texto plano sin attachments |

**EmergencyTypes disponibles (implícito):**

| Tipo | Canales recomendados | Template típico |
|------|---------------------|-----------------|
| `security` | push, sms, whatsapp | "Alerta de seguridad: {detalle}. Evacuar área {zona}" |
| `weather` | push, sms, whatsapp | "Alerta meteorológica: {fenómeno}. Refugio en {lugar}" |
| `health` | push, email | "Alerta sanitaria: {detalle}. Medidas: {acciones}" |
| `evacuation` | push, sms, whatsapp | "EVACUACIÓN INMEDIATA: {razón}. Punto de reunión: {lugar}" |

**Frontend destino:** `EmergencyBroadcast.tsx` (crear), `ApprovalQueue.tsx` (doble confirmación — badge rojo pulsante)

### Tool 3: `send_personalized_notification` — 🟡→🔴 SEMI_AUTO con escalación condicional

**Propósito:** Notificación personalizada a miembros específicos. Escala a HITL si >100 destinatarios.

**Parámetros de entrada:**

| Param | Tipo | Requerido | Default | Validación |
|-------|------|-----------|---------|-----------|
| title | str | Sí | "" | — |
| body | str | Sí | "" | — |
| channel | str | No | "email" | **Canal único, no multi-canal** (diferente a broadcast) |
| recipient_ids | str | Sí | "" | CSV → lista de IDs |
| notes | str | No | "" | — |
| requested_by | str | No | "system" | — |

**Flujo de escalación:**

```
recipient_ids CSV → split por "," → len(recipients)
  ≤ 100 → AUTO: envía directamente
  > 100 → HITL: approval_engine → pending → execute post-aprobación
```

**Flujo AUTO (≤100):**
1. Parsea recipients
2. Crea `CreatePersonalizedNotification`
3. Marca como SENT
4. Crea log con `recipient_count=len(recipients)`

**Flujo HITL (>100):**
1. Parsea recipients
2. Crea approval request con `affected_count=len(recipients)`
3. Post-aprobación → `execute_personalized_notification()` — mismo flujo que AUTO

**Shape de respuesta (AUTO):**

```json
{
  "status": "success",
  "message": "📬 Notificación '{title}' enviada a X destinatario(s) por email.",
  "notification": {
    "id": "uuid",
    "title": "string",
    "body": "string",
    "channel": "email",
    "recipient_ids": ["uuid", "uuid"],
    "status": "sent",
    "sent_at": "ISO datetime",
    "created_by": "string"
  }
}
```

**Shape de respuesta (HITL):**

```json
{
  "status": "pending_approval",
  "request_id": "uuid",
  "message": "📬 Notificación '{title}' para X destinatarios. Requiere aprobación (>100).",
  "details": {
    "title": "string",
    "channel": "email",
    "recipient_count": 150
  }
}
```

**Hallazgos:**

| # | Hallazgo | Severidad | Impacto |
|---|---------|-----------|---------|
| 1 | **Canal único** — broadcast es multi-canal pero personalized es single-channel | MEDIA | Socio que no revisa email no recibe notificación personalizada |
| 2 | **Sin personalización real del body** — `body` es el mismo texto para todos los destinatarios | ALTA | "Personalized" es un nombre engañoso. Sin `{{name}}`, `{{balance}}`, `{{tier}}` variables |
| 3 | **`recipient_ids` es CSV string** — con 150 IDs UUID, el string es ~5,500 caracteres | MEDIA | Límite de query params en algunos proxies. Debería ser array |
| 4 | Sin validación de que recipient_ids existan en la base de socios | MEDIA | Notificación a IDs fantasma |
| 5 | Sin tracking de delivery por recipient — solo log global con recipient_count | ALTA | No sabes si Juan Pérez recibió o no |
| 6 | Sin open/click tracking | ALTA | Sin métricas de engagement por notificación |
| 7 | **Threshold hardcodeado a 100** — no es configurable | BAJA | Cambiar requiere deploy |
| 8 | Sin rate limiting — puede enviar 100 notificaciones en 1 segundo | MEDIA | Spam a socios, posible bloqueo por email providers |

**Frontend destino:** `CommunicationCenter.tsx` (enviar), `ApprovalQueue.tsx` (si >100)

### Tool 5: `schedule_notification` — 🟢 AUTO

**Propósito:** Programar notificaciones para envío futuro usando templates existentes.

**Multi-action:**

| Action | Descripción |
|--------|-------------|
| `list` | Listar notificaciones programadas |
| `get` | Obtener programación por ID |
| `create` | Programar nueva notificación |
| `cancel` | Cancelar programación |

**Parámetros para `create`:**

| Param | Tipo | Requerido | Default | Validación | Notas |
|-------|------|-----------|---------|-----------|-------|
| template_id | str | Sí | — | Validado contra repo (existe?) | |
| recipient_ids | str | Sí | — | CSV → lista | |
| channel | str | No | "email" | Validado contra enum | Canal único |
| scheduled_at | str | Sí | — | Sin formato | **Sin validación de fecha futura** |
| params | str | No | "" | CSV key=value → dict | Variables para renderizar template |
| notes | str | No | "" | — | |

**Formato de `params`:**
```
"nombre=Juan,nivel=platino,fecha=2025-04-15"
→ {"nombre": "Juan", "nivel": "platino", "fecha": "2025-04-15"}
```

**Shape de respuesta (create):**

```json
{
  "status": "success",
  "message": "⏰ Notificación programada para {scheduled_at} (X destinatarios).",
  "scheduled": {
    "id": "uuid",
    "template_id": "uuid",
    "recipient_ids": ["uuid"],
    "channel": "email",
    "scheduled_at": "ISO datetime",
    "params": {"key": "value"},
    "status": "pending",
    "notes": "string"
  }
}
```

**Hallazgos:**

| # | Hallazgo | Severidad | Impacto |
|---|---------|-----------|---------|
| 1 | **Sin validación de `scheduled_at` como fecha futura** — puede programar para ayer | MEDIA | Notificación que nunca se envía o se envía inmediatamente |
| 2 | **Sin motor de ejecución visible** — ¿qué procesa las notificaciones programadas? ¿Cron job? ¿Celery? ¿Nada? | ALTA | Si no hay scheduler, las notificaciones programadas nunca se envían |
| 3 | `params` como CSV key=value es frágil — valores con comas o "=" rompen el parsing | MEDIA | `notes=Reunión a las 3, confirmar` → split incorrecto |
| 4 | Sin validación de que las `params` cubren todas las `variables` del template | MEDIA | Template con `{{name}}` pero params no incluye name → variable vacía en el email |
| 5 | Sin conflict detection — puede programar 50 notificaciones al mismo tiempo | MEDIA | Spike de envío, posible rate limit de email provider |
| 6 | Sin retry on failure — si el envío falla a la hora programada, no reintenta | ALTA | Notificación perdida silenciosamente |
| 7 | `cancel` marca como CANCELLED pero ¿qué pasa si ya se envió? | BAJA | Estado inválido: sent + cancelled |

**Frontend destino:** `CommunicationCenter.tsx` (scheduler UI)

**Parámetros de entrada:**

### Resumen Ejecutivo CommunicationAgent

**Arquitectura:**
- 8 tools: 2 HITL (announcement, emergency), 1 SEMI_AUTO→HITL (personalized), 1 SEMI_AUTO (board package), 4 AUTO (templates, schedule, history, preferences)
- Patrón multi-action en templates, schedule, preferences
- Patrón de escalación condicional: `PERSONALIZED_NOTIFICATION_HITL_THRESHOLD = 100`
- ALWAYS_HUMAN para emergencias (doble confirmación)
- Repository pattern: `CommunicationRepository`

**Modelos usados (11):**

| Modelo | Uso |
|--------|-----|
| `AnnouncementType` | Tipos de anuncio |
| `AnnouncementStatus` | Estados de anuncio |
| `EmergencyType` | Tipos de emergencia |
| `NotificationChannel` | Canales (email, push, sms, whatsapp, in_app) |
| `NotificationStatus` | Estados de notificación |
| `FrequencyPreference` | Frecuencias (realtime, daily, weekly, monthly, never) |
| `TemplateCategory` | Categorías de template |
| `CreateAnnouncement` | Input model announcement |

**Gaps críticos para el frontend:**

**KPIs que FALTAN (requiere nuevo tool o analytics layer):**

| KPI | Cálculo | Necesidad |
|-----|---------|-----------|
| Open Rate | `opens / delivered × 100` | Tracking pixel en emails, evento en push |
