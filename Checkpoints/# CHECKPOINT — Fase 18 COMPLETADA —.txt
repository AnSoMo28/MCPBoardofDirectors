### Patrón: HITL Flow en Forms (consolidado)

```typescript
// Cuando mutation es HITL:
const mutation = useMCPMutation(server, tool, {
  onSuccess: (data) => {
    const payload = data?.data;
    if (payload?.status === "pending_approval") {
      showToast({ type: "info", message: "Solicitud enviada — pendiente de aprobación" });
      navigate("/admin/...");
      return;
    }
    // Normal success flow
    showToast({ type: "success", message: "..." });
    navigate(`/admin/.../${payload?.id}`);
  },
});
```

**Implementado en:**
- ✅ FamilyForm (Fase 17 — create_family, update_family)
- ✅ EventForm (Fase 18 — event_create)
- ✅ EventCalendar QuickAdd (Fase 18 — event_create)
- ✅ EventDetail (Fase 18 — update_event_status)

### Patrón: Backend-Aligned Types con Prefix

**Cuando los types viejos no pueden eliminarse porque componentes dependen de ellos:**

```typescript
// Prefix Bk para nuevos types sin colisión
export type BkEventStatus = "draft" | "pending_approval" | ...;
export interface BkEventResponse { ... }

// Los componentes se migran gradualmente de Event → BkEventResponse
// Cuando todos migrados → eliminar prefix, eliminar types viejos
```

**Implementado:** `types.ts` de events con prefix `Bk` para todos los types nuevos. Los types viejos se mantienen temporalmente pero ya NO se usan en ningún componente post-Fase 18.

## 4. DECISIONES DE DISEÑO

| # | Decisión | Alternativa descartada | Razón |
|---|---------|----------------------|-------|
| D1 | Prefix `Bk` para types backend-aligned | Renombrar in-place (eliminar types viejos) | Componentes legacy dependen de types viejos. Prefix permite migración gradual sin romper nada |
| D2 | `ScoreGauge` extraído a shared | Mantener local en cada IntelligencePanel | 2 módulos ya lo necesitan (families, events). Patrón confirmado para Finance, Wellness |
| D3 | `event_get_calendar` como tool principal del Calendar (no `list_events`) | Mantener `list_events` | Backend real usa `event_get_calendar` como tool. Calendar view necesita CalendarDay[] con has_conflicts |
| D4 | EventDetail 5 tabs en vez de 3 | Mantener 3 (program, rsvps, insights) | Backend devuelve programs[], vendors[] en EventResponse. Separar en tabs mejora scaneo. Proveedores tiene suficiente data para su propia sección |
| D5 | `inputClass` de FormField en QuickAddPanel | Mantener classNames inline | P7: consistencia con patrón del proyecto. Los inline classNames eran visualmente idénticos pero no mantenibles |
| D6 | Botón "Enviar Invitaciones" en EventDetail Actions | Crear integration directa con communication server | Navegar a `/admin/communications?event_id=...&action=invite` es más limpio — communication module ya tiene su UI |
| D7 | `AiAnalysisSection` inline eliminado de EventDetail → `EventIntelligencePanel` componente separado | Mantener inline con on-demand | Separa concerns. El panel AI es reutilizable y puede evolucionar independientemente del detail |
| D8 | `createMockEventGetDetail` con datos completos (programs + rsvps + vendors) | Mock minimal | Testing completo de EventDetail requiere todos los sub-collecciones. Datos CR realistas para demo |
| D9 | `event_create` factory devuelve `pending_approval` (HITL) | Devolver success directo | Simula comportamiento real del backend HITL. Testing del flujo completo incluyendo path de "pendiente" |
| D10 | EventCalendar QuickAddPanel crea evento con `event_create` (HITL) en vez de bypass | Quick add sin approval | Consistencia: TODOS los eventos requieren approval según el backend. Quick add es conveniencia, no bypass |
| D11 | Bloques 7B (Event↔Guest) y 7C (Event↔Families) postergados a Fase 19 | Incluir en Fase 18 | Fase 18 ya es extensa (~2,800 líneas). Cross-module integration merece atención dedicada |
| D12 | `Input.tsx` glass inline (P6) postergado a auditoría shared/ui | Fix en esta fase | No se analizó Input.tsx en Bloque 0. Cambiar shared/ui sin auditoría completa riesga regression |
| D13 | Conflicto detection visual en Calendar via ring+badge rojo | Tool AI separada para conflict detection en Calendar | `CalendarDay.has_conflicts` del backend ya detecta conflictos data-level. La ring visual es suficiente para el calendar. Análisis profundo queda en AI panel |

## 11. DECISION LOG

| Fecha | Decisión | Razón | Impacto |
|-------|---------|-------|---------|
| Jun 2025 | Prefix `Bk` para types backend-aligned de events en vez de renombrar in-place | Types viejos se mantienen hasta que se verifique que ningún componente los usa. Prefix evita romper imports existentes | Fase 21/QA: eliminar types viejos cuando se confirme que no se usan |
| Jun 2025 | `ScoreGauge` extraído a shared/components/ui | 2 módulos lo necesitan (families, events). Pattern confirmado para Finance, Wellness | Fase 19+: importar de shared, no redefinir local |
| Jun 2025 | `event_get_calendar` como tool principal del Calendar (no `list_events`) | Backend real usa esta tool. CalendarDay incluye has_conflicts que el calendar necesita mostrar | `list_events` queda como legacy. En migration decidir si se elimina |
| Jun 2025 | EventDetail 5 tabs (resumen, programa, rsvps, proveedores, ai) | Backend devuelve programs[], vendors[] en EventResponse. Separar mejora scaneo. AI panel merece tab propio | EventDetail más complejo pero más completo |
| Jun 2025 | `AiInsightsPanel` inline ELIMINADO de EventDetail | Auto-loaded AI viola Regla #19. Reemplazado por `EventIntelligencePanel` on-demand | UI consistente con patrón AI del proyecto |
| Jun 2025 | EventForm: 21 campos en vez de 16 | Backend EventCreate tiene 21 campos. Los 5 faltantes (event_type, is_members_only, allow_guests, recurrence, dress_code) son esenciales para el modelo de negocio | Form más extenso pero alineado con backend real |
| Jun 2025 | QuickAddPanel crea evento con HITL approval | TODOS los eventos requieren approval según backend. Quick add es conveniencia, no bypass de approval flow | showToast info + navigate away en vez de success directo |
| Jun 2025 | `useEffect` pattern en EventForm en vez de `onSuccess` deprecated | TanStack v5 deprecated onSuccess en useQuery | Previene warnings y future breakage |
| Jun 2025 | Bloques 7B/7C postergados a Fase 19 | Fase 18 ya es extensa (~2,800 líneas). Cross-module integration merece atención dedicada | Fase 19 incluye Event↔Guest y Event↔Family integration |
| Jun 2025 | Backend gaps documentados (P16-P19): get_event, update_event, update_event_status, AI tools no expuestas | Frontend funciona con mocks. Backend migration en Fase 22 necesita crear estas tools | Fase 22: priorizar get_event + update_event_status primero |
| Jun 2025 | `inputClass` de FormField usado en Calendar QuickAddPanel | P7: consistencia con patrón del proyecto | Inputs visualmente idénticos pero mantenibles |
| Jun 2025 | Botón "Enviar Invitaciones" navega a communications con query params | Más limpio que integration directa. Communication module ya tiene su UI | Cross-module sin tight coupling |
| Jun 2025 | Conflict detection visual en Calendar via ring rose + badge (NO tool AI separada) | CalendarDay.has_conflicts del backend ya detecta conflictos. Ring visual es suficiente para calendar. AI conflict_detection es para análisis profundo en EventDetail | No duplicar funcionalidad |
