## 3. PATRONES ESTABLECIDOS

### Patrón NUEVO: Decision Simulation con 3 Escenarios

**Cuándo se usa:** Cuando se necesita evaluar una decisión estratégica con múltiples outcomes posibles.

```
1. Input: textarea en lenguaje natural (on-demand, Rule #19)
2. AI genera: 3 escenarios (optimista/base/pesimista)
3. Cada escenario: probability %, revenue delta, membership delta,
   cash flow delta, implementation cost, ROI, risk level,
   timeline months, risk factors, key assumptions
4. AI Recommendation: escenario recomendado + confidence bar +
   reasoning + critical success factors + watch items + KPIs
5. Historical Precedents: decisions pasadas del club con outcome real
6. Sensitivity Notes: factores que alteran los resultados
```

**Implementación:** DecisionCockpit.tsx
**Se replica en:** Cualquier evaluación de decisión estratégica (membership pricing, amenity investment, event strategy)

### Patrón NUEVO: Generative Content con Preview + Alternatives

**Cuándo se usa:** Cuando un LLM genera contenido personalizado (comunicaciones, campañas).

```
1. Input: selector de audiencia + parámetros (on-demand, Rule #19)
2. AI genera contenido con: subject, body, preview_text, CTA
3. Tone Analysis: 4 barras (formality, warmth, urgency, personalization)
4. Personalization Details: campos específicos con impacto en engagement
5. Past Performance: historial de comunicaciones previas a la misma audiencia
6. Alternative Versions: tabs con versiones para otros canales
7. Copy + Send buttons
```

**Implementación:** PersonalizedCommunication.tsx
**Se replica en:** Cualquier generación de contenido personalizado (emails, SMS, push notifications, documentos)

### Patrón NUEVO: Campaign Builder con A/B Variants

**Cuándo se usa:** Cuando se genera una campaña completa con múltiples variantes.

```
1. Input: segment grid + objective textarea + channel selector (on-demand)
2. AI genera: campaign name, objective, audience breakdown (tier/segment/engagement)
3. A/B Variants: tabs selector, cada variante con subject, body, CTA, hypothesis
4. Channel Strategy: primary/secondary, timing, frequency, escalation rule
5. Expected Metrics: open/click/conversion/unsubscribe % vs benchmark
6. Schedule: draft/review/launch/end dates
7. Compliance Notes: checklist regulatorio
8. "Programar Campaña" button con toast SEMI
```

**Implementación:** CampaignGenerator.tsx
**Se replica en:** Cualquier campaña de marketing, promoción, evento

## 4. DECISIONES DE DISEÑO

| # | Decisión | Alternativa descartada | Razón |
|---|---------|----------------------|-------|
| 1 | Fase 15ext antes que pendientes MEDIA | Resolver deuda técnica primero | Momentum de features nuevas. Pendientes se agrupan en Fase 15 (QA) que es el paso natural |
| 2 | Nuevo server `operations` en registry | Reutilizar `executive_dashboard` o crear `facility_management` | Las 3 tools son de operaciones diarias, no de dashboard ejecutivo ni de gestión de instalaciones. Server autónomo. |
| 3 | DailyBriefing staleTime 60s | staleTime 300s como otros auto-loads | Datos operativos cambian rápido (eventos del día, alertas staff). El staff necesita info lo más fresca posible cada vez que abre la app |
| 4 | SmartSchedule on-demand en vez de auto-load | Auto-load como DailyBriefing | El schedule de "mañana" o "la próxima semana" no tiene sentido cargar automáticamente. El staff elige qué fecha optimizar |
| 5 | ComplianceCheck auto-load | On-demand como SmartSchedule | Compliance es monitoreo continuo — el staff revisa regularmente. No requiere intención explícita |
| 6 | DecisionDocument: 4 fuentes en vez de 3 | Mantener 3 fuentes | El usuario pidió explícitamente agregar finance_decision_simulate como 4ta fuente. Enriquece el documento con análisis de decisiones |
| 7 | DecisionCockpit como tab #8 en FinancialIntelligence | Nuevo módulo independiente | Vive junto a ScenarioSimulator y StressTest — flujo natural: explorar → simular → decidir |
| 8 | SentimentMonitor como 3er tab nuevo en CommunicationDashboard | Sub-tab de "Analytics" existente | Sentiment es una disciplina diferente a analytics de comunicación (open rates, clicks). Merece su propio tab |
| 9 | Personalization y Campaigns como tabs separados | Un solo tab "Generativa" | Cada herramienta tiene un flujo de trabajo diferente y diferentes parámetros de entrada. Separar reduce la complejidad cognitiva |
| 10 | OperationsDashboard usa DetailTabs | Sub-tabs manuales como FinancialIntelligence | 3 tabs simples que no necesitan sub-tabs anidados. DetailTabs es el componente shared estándar para hubs |
| 11 | Visual timeline con ml-24/32 border-l en vez de Recharts | Gantt chart con librería externa | Recharts no tiene Gantt nativo. El timeline visual es más simple, más accesible y consistente con el stack. Los bloques expandibles dan suficiente detalle |
| 12 | Compliance items como table + expandible cards | Solo cards o solo table | Table para desktop da densidad informativa. Cards expandibles para mobile dan progressive disclosure (Rule #21) |
| 13 | Filter pills en compliance con aria-pressed | Dropdown select | Pills son más visibles y permiten toggling rápido. El usuario ve todos los estados disponibles sin abrir un dropdown |
| 14 | Weather card inline en DailyBriefing | Sección dedicada más grande | Weather es contexto, no feature principal. Inline mantiene el briefing compacto |
| 15 | 24 items de compliance con regulaciones CR reales | Mock genérico con items genéricos | El club opera en Costa Rica — las regulaciones deben ser reales: Ley 8968 (datos), Ley 8098 (bomberos), SETENA, facturación MH, CCSS, INS |
