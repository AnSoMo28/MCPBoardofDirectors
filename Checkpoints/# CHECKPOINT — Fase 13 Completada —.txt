## 3. PATRONES ESTABLECIDOS

### Patrón NUEVO: Simulador de Escenarios con Sliders

**Cuándo se usa:** Cuando hay variables ajustables que impactan un output proyectado.

```
1. Variables agrupadas por categoría (pricing, membership, expense, revenue)
2. Slider HTML nativo con type="range"
3. Label + valor actual con color dinámico (verde si > default, rojo si < default)
4. Min/default/max labels debajo del slider
5. Delta cards: baseline → escenario con arrow y valor delta coloreado
6. Risk cards con severity, probability, affected segments
7. AI commentary como narrative final
```

**Ejemplo:** ScenarioSimulator en FinancialIntelligence.tsx
**Se replica en:** Futuros simuladores (membership pricing, event pricing, staffing)

### Patrón NUEVO: Scanner de Oportunidades con Action Flow

**Cuándo se usa:** Cuando el sistema identifica activamente items que requieren decisión del usuario.

```
1. Summary strip con KPIs (count, revenue potencial, quality score, high confidence count)
2. Category filter chips con toggle (click para filtrar, click de nuevo para limpiar)
3. Opportunity cards con:
   - Title + status badge (NEW → reviewed → approved → implemented → dismissed)
   - Category badge + time to revenue
   - Description narrative
   - Confidence bar + effort badge + affected segments
   - Data basis (qué datos lo fundamentan)
   - Risk factors alert box
   - Action buttons: Implement / Program / Descartar
```

**Ejemplo:** OpportunityScanner en FinancialIntelligence.tsx
**Se replica en:** Cualquier feature de recomendaciones activas (wellness, satisfaction)

### Patrón NUEVO: Briefing Ejecutivo con Decisiones

**Cuándo se usa:** Cuando se genera un resumen ejecutivo para tomadores de decisión.

```
1. Header bar con metadata (period, generated_at) + actions (Regenerar, PDF, Enviar)
2. Key metrics grid (4 KPIs con trend arrows y assessment colors)
3. Sections con severity lateral bars (info/highlight/alert/critical)
4. Items list con emoji extraction → icono Lucide
5. Alerts con severity + requires_action flag
6. Recommendations priorizadas con estimated impact
7. Upcoming decisions con options (A, B, C...), deadline, impact estimate
```

**Ejemplo:** BoardBriefing en FinancialIntelligence.tsx
**Se replica en:** Cualquier briefing/report ejecutivo (board, AGM, investor)

### Patrón NUEVO: Section Wrapper Expandible

**Cuándo se usa:** Cuando un componente tiene 3+ secciones colapsables.

```
Section({
```

## 4. DECISIONES DE DISEÑO

| # | Decisión | Alternativa descartada | Razón |
|---|---------|----------------------|-------|
| 1 | FinancialDashboard con 6 tabs (no 5) | 5 tabs (sin Inteligencia) | 3 features de inteligencia (Simulator, Opportunities, Briefing) merecen su propio tab. Son herramientas de alto valor que no deben esconderse en "Herramientas" |
| 2 | `get_financial_summary` como bridge mock | Reescribir todo para usar solo tools del agente | Factory provee sparklines + change_pct que las tools del agente no tienen. El bridge permite que FinanceOverview funcione sin cambios cuando backend implemente la tool |
| 3 | `generate_ai_analysis` como auto-load con staleTime 5min | Botón on-demand (como communication_insights) | Backend ya computa el analysis — no es mock-only. Carga automática da UX inmediata. Botón "Regenerar" para forzar refresh |
| 4 | ScenarioSimulator con sliders HTML nativos | Componente de slider custom | 6 variables necesitan controles inmediatos. Sliders nativos son accessibility-first (funcionan con teclado/screen reader sin custom code) |
| 5 | ScenarioSimulator auto-simula al cambiar variables | Botón "Simular" explícito | UX más fluida — el usuario ve el impacto en tiempo real. staleTime 5min evita requests excesivos. Botón "Simular" hace refetch explícito |
| 6 | OpportunityScanner con 3 acciones (Implement/Program/Descartar) | Solo "Implementar" | Workflow completo — el admin necesita poder archivar oportunidades o programarlas para revisión futura |
| 7 | Briefing con "Enviar a Junta" button placeholder | Solo preview | El flujo completo de envío requiere backend de notificaciones. El placeholder comunica la intención |
| 8 | Decision options como cards numeradas (A, B, C) | Radio buttons | Más visual y apropiado para decisiones ejecutivas. Las opciones son informativas, no un form |
| 9 | FamilyAccount rewrite completo (no quirúrgico) | Patches individuales | Los 3 fixes (#11, #12, #13) + mobile cards tocaban secciones intercaladas — un rewrite limpio es más seguro que 3 patches |
| 10 | BACKEND_TIER_CONFIG + mapping functions | Reemplazar frontend tiers completamente | Componentes existentes usan "platino"/"oro"/"plata"/"bronce". Mapping bridgea ambos mundos sin romper nada |
| 11 | `getInvStatusConfig()` helper inline en BillingCenter | Agregar draft/sent a INVOICE_STATUS_CONFIG global | Solo BillingCenter necesita estos status. No contaminar el config global para 2 valores |
| 12 | BudgetManager con inline edit (no modal) | Modal de edición por categoría | Cambiar un valor de presupuesto es una acción simple. Inline edit es más rápido y contextual |
| 13 | ReportGenerator con date range pickers | Period selector (monthly/quarterly/yearly) como BudgetManager | Reports necesitan granularidad de fecha. Un trimestre específico es diferente a "este trimestre" |
| 14 | 3 families hardcodeadas en FamilyPresets (BillingCenter) | Dynamic family search | Para mock, 3 presets dan contexto inmediato. El input libre permite custom IDs. Backend eventualmente proveerá search |
| 15 | Category chips con toggle en OpportunityScanner | FilterDropdown | 6 categorías como chips son más visuales y permiten ver totales por categoría inline |

## Feature 4 — Matriz de Rentabilidad por Socio (Member Profitability Matrix)

### Qué es

Un mapa visual de cada socio/familia en dos dimensiones: cuánto facturan vs cuánto cuestan al club. Cuatro cuadrantes con estrategias diferentes. No es una tabla — es una herramienta de segmentación estratégica que revela verdades incómodas sobre quién subsidia a quién.

### Visualización

```
         ALTO COSTO
              │

    │ Analizar │ Fidelizar│

────┼─────────┼─────────┼──── ALTO REVENUE

    │ contratos│ programas│

    └─────────┼─────────┘
              │
         BAJO COSTO

Hover/focus sobre cada punto → detalle de la familia:
```

### Segmentación AI automática

Los 4 cuadrantes con estrategias diferenciadas:

- **Stars (high rev / low cost):** Fidelizar, ofrecer beneficios exclusivos, evitar migración. Son el motor financiero del club.
- **Workhorses (high rev / high cost):** Optimizar costos de servicio, evaluar si los servicios extra generan ROI. Pueden ser estrellas si se optimiza el costo de atenderlos.
- **Potentials (low rev / low cost):** Activar con programas de consumo, cross-sell actividades. Bajo riesgo, alta oportunidad.
- **Risks (low rev / high cost):** Revisar términos, evaluar si el servicio que consumen justifica su membresía. Conversación difícil pero necesaria.

## Feature 5 — Test de Estrés Financiero (Monte Carlo Stress Test)

### Qué es

Un simulador que evalúa la resiliencia financiera del club ante escenarios adversos. No usa números fijos como el Scenario Simulator — usa distribuciones de probabilidad y ejecuta N iteraciones (Monte Carlo) para generar un fan chart de posibles resultados. Es la diferencia entre saber "si pierdo 10 socios, pierdo X" y saber "hay un 87% de probabilidad de mantener cash flow positivo si viene una recesión".

### Escenarios preconfigurados

```
┌─ Escenario: "Recesión Costa Rica 2026" ──────────────┐
│                                                        │
│ Variables estocásticas:                                │
│ • Churn de socios: μ=8%, σ=3% (distribución normal)  │
│ • Caída F&B: μ=15%, σ=5%                              │
│ • Eventos cancelados: μ=25%, σ=10%                    │
│ • Tipo de cambio USD/CRC: μ=+12%, σ=4%               │
│                                                        │
│ 1,000 iteraciones Monte Carlo                          │
│                                                        │
│ RESULTADO:                                             │
│ ┌────────────────────────────────────────────┐        │
│ │ P(mantener cash flow positivo 12m): 87%    │        │
│ │ P(health score > 60): 72%                  │        │
│ │ Pérdida máxima probable (P95): ₡-18.3M    │        │
│ │ Reserva mínima recomendada: ₡22M           │        │
│ │ Mes más crítico: Agosto 2026               │        │
│ └────────────────────────────────────────────┘        │
│                                                        │
│ Fan chart de 12 meses con P10/P25/P50/P75/P90        │
│ (5 líneas de proyección de cash flow acumulado)       │
└────────────────────────────────────────────────────────┘
```

### 6 Escenarios preconfigurados

1. **"Recesión Costa Rica"** — churn 8%±3%, caída F&B 15%±5%, eventos cancelados 25%±10%, tipo de cambio +12%±4%
2. **"Pandemia 2.0"** — cierre temporal 2 meses, recovery 6 meses, churn 15%±5%, F&B -40%±10%
3. **"Competencia"** — nuevo club abre a 15 min, churn 12%±4%, guest fees -20%, eventos -30%
4. **"Renovación Mayor"** — cierre parcial de instalaciones 6 meses, gastos +50%, revenue -25%
5. **"Boom"** — crecimiento acelerado: +20%±8% socios, +30%±10% eventos, staff +15%
6. **"Custom"** — el usuario define μ y σ para cada variable

### Visualización principal

**Fan Chart (12 meses):**
- 5 líneas: P10 (pesimista), P25, P50 (mediana), P75, P90 (optimista)
- Área sombreada entre P10 y P90 (zona de incertidumbre)
- Línea de referencia en ₡0 (break-even)
- Mes más crítico resaltado con marker

**Metrics panel:**
- P(cash flow positivo 12m): gauge %
- P(health score > 60): gauge %
- Pérdida máxima probable (P95): número grande
- Reserva mínima recomendada: número grande
- Mes más crítico: badge

## Feature 6 — Calendario Financiero Inteligente Estacional

### Qué es

Un timeline visual de 12 meses específico para Costa Rica que muestra patrones estacionales de revenue y gasto, ventanas de acción recomendadas, alertas financieras anticipadas, y eventos programados. No es un calendario genérico — es un mapa temporal que conecta la realidad climática y cultural costarricense con la salud financiera del club.

### Layers toggleables

El componente tiene 6 layers que el usuario puede activar/desactivar:

1. **Revenue patterns** (por categoría): barras apiladas mostrando composición mensual del revenue
2. **Expense patterns** (por categoría): barras apiladas mostrando composición mensual de gastos
3. **Eventos programados**: markers en timeline (bodas, bautizos, quinceañeras, corporativos)
4. **Maintenance windows**: bloques de tiempo donde hay mantenimiento programado (cierre parcial piscina, etc.)
5. **Cash reserve requirements**: línea mostrando cuánto cash necesita el club mes a mes para cubrir obligaciones
6. **AI recommended actions**: cards con acciones específicas por mes, cada una con ahorro/revenue potencial

### Componente propuesto

**SeasonalCalendar.tsx** (~600 líneas)
- **Timeline view** (default): 12 columnas (una por mes), 6 filas (una por layer), toggle por layer
- **Month detail view** (click en columna): expande para mostrar detalle del mes con todos sus eventos, obligaciones, y acciones recomendadas
- **Actions panel**: lista priorizada de acciones recomendadas con estimated impact y deadline
- **Season indicator**: barra horizontal con colores (alta=verde, baja=rojo, transición=ámbar)
- **Legend**: qué significa cada layer
- **Annual summary card**: 6 KPIs (high/low season revenue, gap %, total obligations, critical months, reserve)
- Tool: `finance_seasonal_calendar` (auto, staleTime 1h — datos estacionales no cambian frecuentemente)

### Por qué no en Fase 13

Tres razones:
1. **Puede ser standalone:** No depende de los otros componentes de finance. Se puede construir en cualquier momento.
2. **Los datos estacionales son semi-estáticos:** La seasonalidad CR no cambia trimestre a trimestre. No hay urgencia.
3. **Valor es contextual:** Funciona mejor cuando el club ya tiene los otros dashboards funcionando y puede tomar acciones basadas en las recomendaciones del calendario.

### Cuándo implementar

**Fase 14 o 15**, idealmente junto con Print/PDF (Fase 14) porque:
1. El calendario es altamente imprimible — la junta lo puede tener como referencia física
2. Las "Acciones Recomendadas" se pueden exportar como checklist mensual
3. Los datos semi-estáticos significan que el mock puede ser muy realista desde el día 1
