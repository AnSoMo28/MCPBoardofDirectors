## Contexto — Proyecto Castillo Country Club

Estoy trabajando en una aplicación web React para la gestión integral del **Castillo Country Club**, un club de campo en Costa Rica. Es un SPA construido con:

- **React 19** + **TypeScript**
- **React Router v7** (`createBrowserRouter`)
- **TanStack Query** (`@tanstack/react-query`) para datos del servidor
- **Zustand** para estado local (auth, theme)
- **Framer Motion** para animaciones
- **Lucide React** para iconos
- **Tailwind CSS 4** para utilidades
- **Backend MCP** (Model Context Protocol) — los datos vienen de herramientas MCP, no de REST APIs convencionales. Se acceden via hooks personalizados `useMCPQuery` y `useMCPMutation`.
- No hay API REST tradicional. Todo se comunica via MCP tools.

### Roles del sistema
- **ADMIN** — acceso total
- **STAFF** — operaciones diarias (familias, eventos, instalaciones, invitados, documentos)
- **JUNTA** — directiva (dashboard ejecutivo, reportes, finanzas, engagement)
- **SOCIO** — portal `/mi-club` (su familia, eventos, reservas, cuenta, encuestas)

### Lo que hicimos hasta ahora

Completé una migración masiva de tokens CSS llamada **"Silver Tide"**. El proyecto tenía un sistema de CSS custom properties inconsistente con tokens semánticos antiguos (`--color-charcoal`, `--color-stone`, `--color-cream`, `--color-forest`, `--color-gold`, `--color-border`, `--color-surface`, etc.) que referenciaban colores hardcoded como fallbacks.

Migramos **todos los componentes** (~40 archivos) a un sistema unificado:

**Token Map Silver Tide:**
--color-charcoal → --color-silver-200 (texto principal)
--color-stone → --color-silver-400 (texto muted)
--color-cream → --color-surface-1 (superficies)
--color-forest → --color-emerald-400 (éxito/positivo)
--color-gold → --color-gold-400 (acento)
--color-error → --color-rose-400 (error)
--color-warning → --color-amber-400 (warning)
--color-info → --color-teal-400 (info)
--color-border → border-white/[0.06] (bordes)
--color-surface → --color-surface-1 (fondos)
bg-white + dark:bg- → bg-[var(--color-surface-1)] (merge light/dark)
dark:text- → text-[var(--color-silver-200)] (merge)

También se reemplazaron:
- `rgba()` hardcoded en bgColors → `color-mix(in srgb, var(--color-xxx) N%, transparent)`
- `focus:ring-2 focus:ring-[var(--color-gold)]/20` → `focus:outline-2 focus:outline-[var(--color-gold-400)]`
- Colores Tailwind rojos/verdes en errores/éxitos → variables del tema

¿Qué sigue? — Perspectiva Senior

1. Validar la fundación (index.css) — PRIORIDAD ALTA


Todo lo que migramos depende de que los tokens Silver Tide estén definidos en algún lugar. Si index.css no tiene :root { --color-silver-200: ...; --color-silver-400: ...; }, nada funciona. Este es el paso más crítico antes de cualquier otra cosa.


2. QA visual con ambos temas


La migración mergeó dark: prefixes en muchos lugares. Necesitás abrir la app, recorrer cada página en modo claro y modo oscuro, y verificar que:

El texto sea legible en ambos temas
Los bordes se vean
Los badges tengan contraste suficiente
Los hover states funcionen

3. LoginPage.tsx


Es el único componente feature no migrado. Un archivo, lo resolvemos rápido.


4. Error boundaries y loading states


No vi ErrorBoundary components en el router. Para producción necesitás:

Un error boundary a nivel de feature (cada route)
Un fallback global en el router
Loading states consistentes (ya tenés Skeleton, pero ¿están en todas las páginas?)

5. Auth flow real


El devBypass() en App.tsx es temporal. Para producción necesitás:

Flujo de login real contra el backend
Persistencia de sesión (JWT/token refresh)
Manejo de expiración de sesión
Redirect a /login cuando no esté autenticado
