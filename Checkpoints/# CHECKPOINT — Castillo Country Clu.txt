## ARQUITECTURA BACKEND: MCP AGENTS
El backend NO es una REST API tradicional. Son agentes autónomos que se comunican vía MCP (Model Context Protocol). Cada agente tiene tools (funciones) que el frontend invoca así:

useMCPQuery(serverName, toolName, params)
useMCPMutation(serverName, toolName, options)

El servidor real es /api/agents/{server}/{tool} (POST).

## SISTEMA DE MOCKS (contracts → factories → registry)
Creamos un sistema type-safe de mocks para desarrollo sin backend:

src/shared/mocks/
├── contracts.ts        ← Define el shape EXACTO de cada tool response
├── factories.ts        ← Factory functions que satisfacen contracts
└── mock-registry.ts    ← Mapea "server.tool" → factory

Resolución en api.ts:
1. mock-registry.ts (typed, síncrono) — mocks nuevos
2. mock-data.ts (legacy, con simulateDelay) — fallback
3. { status: "success", message: "OK" } — last resort

Para migrar un tool a backend real:
1. Eliminar la key de MOCK_REGISTRY en mock-registry.ts
2. Eliminar la key de mock-data.ts si existe
3. callMCPTool() hace fetch al backend automáticamente
4. 0 cambios en componentes

## AGENTES BACKEND Y SUS TOOLS

### ExecutiveDashboardAgent (server: "executive_dashboard")
- get_executive_summary → Summary KPIs, revenue, tiers, activities, anomalies, HITL, age balance, YoY
- get_financial_overview → Financial data for dashboard
- get_membership_health → Membership metrics
- get_operational_pulse → Operational metrics
- detect_anomalies → Anomaly detection
- get_age_group_balance → Age distribution analysis

### FinanceAgent (server: "finance")
- get_financial_summary → Revenue, expenses, margins, cash flow, AR aging, expense breakdown
- generate_ai_analysis (scope: "financial") → Health score, cash flow forecast, concentration, anomalies, member economics, recommendations

### MemberEngagementAgent (server: "member_engagement")
- get_engagement_dashboard → Family engagement scores, levels, trends, risk factors, distribution
- generate_ai_analysis (scope: "engagement") → Churn analysis, critical families, retention strategies, financial impact

### WellnessAgent (server: "wellness")
- wellness_report → Activity breakdown, minutes, calories, goals, streak

### SatisfactionAgent (server: "satisfaction")
- get_satisfaction_trends → NPS, category averages, sentiment flow, improvements, quotes

### ProactiveRecommendationAgent (server: "proactive_recommendation")
- identify_social_clusters → Social clusters with shared interests
- generate_quarterly_insights → Quarterly business insights
- detect_scheduling_conflicts → Event scheduling conflicts

### CommunicationAgent (server: "communication")
- broadcast_club_announcement (HITL) → Club announcements
- manage_emergency_broadcast (ALWAYS_HUMAN) → Emergency broadcasts with dual approval
- send_personalized_notification (HITL) → Personalized messages
- manage_notification_templates → CRUD templates
- schedule_notification → CRUD scheduled notifications
- get_notification_history → Notification log
- list_announcements → List/filter announcements
- get_communication_analytics → Communication stats
- send_board_package → Board package generation

### HITLAgent (server: "hitl")
- get_pending_approvals → Pending approval queue
- approve_request → Approve a pending request
- reject_request → Reject a pending request

## SUGERENCIAS PROACTIVAS

### AI Integration
1. Cada sección del dashboard debería tener su propio AIDecisionPanel con scope específico
2. Los AI reports deben cachearse (TanStack Query staleTime) para no re-generar en cada visita
3. Considerar un "AI Insights" global en el sidebar que muestre los anomalies más críticos de todos los agentes
4. Los AI analysis deberían tener un historial (últimos 5 reports) para comparar evolución

### Agent Integration
1. CommunicationAgent tiene 9 tools — el CommunicationCenter debería ser un hub con tabs para cada función
2. El HITL queue debería subscribirse a updates en real-time (WebSocket o SSE) en vez de polling cada 30s
3. ProactiveRecommendationAgent debería alimentar un "Smart Suggestions" widget en el dashboard
4. WellnessAgent y SatisfactionAgent deberían combinarse en un "Member Health" view unificada

### Mock → Backend Migration Strategy
1. Migrar en orden de dependencia: HITL primero (ya está), luego ExecutiveDashboard, luego Finance
2. Cada tool migrado se quita del registry y se testea
3. Los contracts NUNCA se borran — son el source of truth del shape
4. Mantener factories como test fixtures para tests unitarios futuros

### Technical Debt
1. mock-data.ts legacy debe eliminarse gradualmente
2. Los componentes de Fase 6 (Engagement, Communications, Approvals) deberían consumir directamente de useMCPQuery en vez de recibir props del padre
3. Crear un hook genérico useMCPDashboard que combine query + AI analysis + refetch
4. Los charts deberían tener un wrapper <SilverTideChart> que aplique CHART defaults automáticamente
