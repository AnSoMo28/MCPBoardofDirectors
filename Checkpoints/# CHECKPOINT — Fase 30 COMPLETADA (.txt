## 4. PATRONES ESTABLECIDOS / ACTUALIZADOS

### Patrón NUEVO: Type System Unification Layer (F30)

**Concepto:** Un archivo maestro `domain-enums.ts` define TODOS los enums cross-domain. Cada domain types.ts importa de aquí. Cuando el backend cambia, se actualiza UN archivo.

**Cuándo se aplica:** SIEMPRE que un concepto se usa en 2+ domains.
**Archivos:** `shared/types/domain-enums.ts`
**Patrón de importación:**
```typescript
import { type EventCategory, EVENT_CATEGORY_DISPLAY } from "@/shared/types/domain-enums";
```

### Patrón NUEVO: AI Intelligence Type System (F30)

**Concepto:** Tipos genéricos (`AIPrediction<T>`, `AIAnalysis`, `AIBrief`) que se extienden por domain.

**Cuándo se aplica:** Cada vez que un domain crea inteligencia AI.
**Archivos:** `shared/types/ai-intelligence.ts`
**Patrón de extensión:**
```typescript
interface FinancialAnalysis extends AIAnalysis {
  domain: "financial";
  cash_flow_forecast?: { ... };
}
```

### Patrón NUEVO: Conditional HITL Escalation (F30 — sports_recreation)

**Concepto:** Tool AUTO que escala a HITL basado en parámetros (ej: `purpose == "tournament_block"`).
**Ejemplo:** `manage_court_reservations` — AUTO para reservas regulares, HITL para bloqueos de torneo.

### Patrón NUEVO: Multi-Source Intelligence (F30 — sports_recreation)

**Concepto:** Tool de recomendación que combina múltiples fuentes de datos internas para generar recommendations con confidence scoring.
**Ejemplo:** `get_sports_recommendations` — combina classes + coaching history + equipment.

### Patrón NUEVO: HITL Auto-Approve (F30 — satisfaction)

**Concepto:** Tool que crea approval request pero lo auto-aprueba inmediatamente. Mantiene trazabilidad sin requerir intervención humana.
**Ejemplo:** `submit_satisfaction_survey` — operación de socio auditable.

### Patrón NUEVO: Legacy CONFIG with Master Enrichment (F30 — engagement migration)

**Concepto:** En vez de eliminar CONFIG locales que los componentes ya consumen, se re-enriquecen usando spread de los display configs del master. Permite migración sin romper componentes.

**Ejemplo:**
```typescript
export const ENGAGEMENT_LEVEL_CONFIG: Record<string, { label: string; color: string; bgColor: string; description: string }> = {
  champion: { ...ENGAGEMENT_LEVEL_DISPLAY.champion, description: "Embajador del club" },
  // Legacy aliases
  thriving: { ...ENGAGEMENT_LEVEL_DISPLAY.champion, description: "Participación activa" },
};
```

**Cuándo se aplica:** Cuando un CONFIG local tiene más campos que el master (ej: description, icon) pero el base viene del master.
**Archivos donde ya implementado:** engagement/types.ts, dashboard/types.ts, members/types.ts.

## 10. DECISIONES DE DISEÑO

| Decisión | Razón | Impacto |
|----------|-------|---------|
| Type System Unification via domain-enums.ts | 5 sistemas de tiers, 2 de age groups causaban inconsistencias | UN archivo maestro reemplaza duplicaciones |
| AI Intelligence Type System via ai-intelligence.ts | Patrones AI repetidos sin reutilización | Generic types + domain aliases |
| Backend como source of truth para enums | Los 7 values de EngagementLevel del backend son más completos | Legacy mappings permiten migración incremental |
| Propuesta 1+3 como eje, 2+4 como vehículo | 1+3 resuelven raíz, 2+4 son operación/transición | Claridad estrategia vs táctica |
| Regla >30% REWRITE | Múltiples cambios quirúrgicos desperdician tokens | Optimización de recursos |
| Domain-specific NO van al master | SportType, CulturalCategory solo se usan en 1 domain | Evita bloat en domain-enums.ts |
| CONFIG locales se re-enriquecen con spread del master | Componentes existentes consumen CONFIG con fields extra (description, icon) | Migración sin romper componentes |
| Dual system Bk* prefix eliminado en events/types.ts | Bk* era placeholder de migración — ya no necesario | Archivo limpio, un solo set de tipos |
| Legacy types ELIMINADOS (no @deprecated) en events | Events era REWRITE completo — más limpio eliminar que mantener | Sin baggage en el archivo más grande |
